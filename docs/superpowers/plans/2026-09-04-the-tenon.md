# The Tenon Implementation Plan

**Status:** implementation complete — all nine tasks complete; awaiting merge.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the value of a `(species, thing)` pair a derived function of traits both kinds already carry, and add the sleepable surfaces without which that function has nothing to relate.

**Architecture:** Each side carries traits; nothing anywhere holds a `(species, thing)` cell. `windows/vessel::ObjectTraits` gains a `RestSurface` (in the same row as the `SupportsRest` marker it depends on); `domains/species` gains a substrate response derived from the `habitat_realm_registry` it already has; and the combining function lives in `windows/vessel::liveness`, naming neither roster's keys. **Tasks 2–6 are byte-identical by construction** — the whole mechanism lands moving no artifact, because `grade(species, bed) == sleep_grade_registry[species]` exactly. **Task 7 is the single epoch**, and it is the only task that moves a world.

**Tech Stack:** Rust 2024, no new dependencies (the workspace allowlist is `serde`, `serde_json`, `libm` only), `cargo nextest`, `ComponentStore<KindId, _>`.

**Spec:** `docs/superpowers/specs/2026-09-04-the-tenon-design.md`

## Global Constraints

- **Layering is constitutional**: `kernel/` → `domains/*` → `windows/*` → `cli/`. A domain crate depends on `hornvale-kernel` and **never** a sibling domain. `cli/tests/architecture.rs` enforces it.
- **No `HashMap` / `HashSet`** — `BTreeMap` / `BTreeSet` / `Vec` only. Enforced workspace-wide by `clippy.toml` `disallowed-types`.
- **No wall-clock time.** No `std::time::Instant`, no `SystemTime`.
- **No new dependencies.** The allowlist is `ALLOWED_EXTERNAL` in `cli/tests/architecture.rs`.
- **Every crate sets `#![warn(missing_docs)]`.** Every public item, field and variant gets a one-line doc comment.
- **Every authored numeric constant** in `domains/*/src` and `windows/*/src` carries a `plumb:` rung tag naming the **axis it varies along** (`universal` / `per-world` / `per-species` / `per-people` / `per-individual`). A reason saying *where the number came from* ("a calibration knob", "a game-design coefficient") answers a neighbouring question and is a review finding. Decision 0586.
- **A `plumb:` tag MUST be one physical line.** `tools/plumb/src/tag.rs:174`
  parses per line (`line.trim().strip_prefix("plumb:")`), so a reason wrapped
  across two `///` lines is read as an unterminated verdict and lands
  **malformed**. Malformed fails `check` exactly like undeclared — pinned by
  `check_fails_on_a_malformed_tag` — so the gate does catch it, but only after
  you run it; nothing in the source reads as wrong. Write the reason long and
  unwrapped, however far past the margin it runs. **Task 2 hit this; do not
  hit it again.**
- **Every primitive at a `pub` boundary** carries a `type-audit:` verdict tag (`bare-ok(<class>)` / `waiver(<reason>)` / `pending(wave-N)`).
- **A `type-audit:` tag goes on the ITEM's own doc comment and names its
  primitives by position** — `bare-ok(ratio: offer)`, `bare-ok(ratio: Natural.0)`
  — never on a field's or a variant's own doc line, where the extractor cannot
  see it (`tools/type-audit/src/tag.rs`: *"the `type-audit:` verdict line inside
  an item's doc comment"*). `windows/vessel/src/brief.rs:41` is the shape to
  copy. **Task 2 hit this too**, on both of its new types, and both tags were
  silently invisible until `type-audit check` refused.
- **A test filter that matches nothing prints a GREEN.** Before trusting any
  red — and especially before trusting the behavioural red each task asks for —
  confirm the filter actually selected the test: `running N tests` with `N > 0`.
  Task 3's plan text said `-- substrate`, which matches **zero** of its two test
  names, so the exact command written to *demonstrate the red* reported
  `running 0 tests ... ok` while the stub was in place. Also check the
  **target**: `--test suite` runs only integration tests, `--lib` runs
  in-module `mod tests`, and this crate's tests live in both.
- **`cargo fmt` is the final step before every commit.** Fmt-gate skips are the most common review finding here.
- **Never `--no-verify`, never `-c core.hooksPath=/dev/null`.** Every commit runs `gate-commit` through the hook.
- **Quantize at emit only** — never in the compute path.
- The gate for every commit is `make gate-commit`; the hook runs it for you.

```rust
/// What a rest surface is made of, from the sleeping body's point of view.
///
/// **Two variants, not a single hardness scalar, because a made surface has
/// no hardness of its own that matters.** 0697's own words: "a made bed is
/// made by, and for, the body that made it." A `Made` surface is fitted to
/// whoever built it, so the sleeper's substrate preference does not
/// discriminate against it and `fit` is `1.0` — the species' own
/// `sleep_grade_registry` row already encodes whether that species can
/// collect the fit half at all (`INSULATION_ONLY` 1.35 is exactly "endotherm,
/// cannot collect fit"), so applying a second fit penalty here would charge
/// it twice.
#[derive(Clone, Copy, Debug, PartialEq)]
pub enum Substrate {
    /// Built by, and sized to, whoever built it.
    Made,
    /// Found rather than made, at this hardness — `0.0` fully yielding,
    /// `1.0` rock.
    /// type-audit: bare-ok(ratio)
    Natural(f64),
}

/// What a kind offers a body that lies down on it (The Tenon).
///
/// **Held in the same row as [`ObjectProperty::SupportsRest`] rather than in
/// a sibling table, and that is a correctness choice.** See
/// [`object_registry`] and `supports_rest_and_a_rest_surface_imply_each_other`.
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct RestSurface {
    /// The fraction of a fully-offering made surface's benefit this kind
    /// gives, in `[0, 1]`. `1.0` is a bed.
    /// type-audit: bare-ok(ratio)
    pub offer: f64,
    /// What the surface is, for the sleeper's substrate preference.
    pub substrate: Substrate,
}
```

## Task 3: the substrate response, derived from `habitat_realm_registry`

**Files:**
- Modify: `domains/species/src/lib.rs` (beside `habitat_realm_registry` at :2509 and `sleep_grade_registry` at :4344)
- Test: `domains/species/tests/suite/coverage.rs`

**Interfaces:**
- Consumes: `hornvale_kernel::ConditionResponse`, `hornvale_species::HabitatRealm`.
- Produces: `pub fn substrate_response(realm: HabitatRealm) -> ConditionResponse`.

**The function takes a RESOLVED realm, not a species name, and that follows an
idiom already in the tree rather than inventing one.** `habitat_realm_registry`'s
own doc states the rule: it is *"sparse rather than a `BiosphereTraits` field
because this has a single consumer (`per_species_suitability`) which holds a
slice, not a row — the consumer-count rule The Long Age established"*. And
`windows/worldgen/src/lib.rs:1631` really does take
`species_realm: &[hornvale_species::HabitatRealm]` — the caller resolves, the
function receives.

Taking the realm buys something a species-keyed signature cannot: **there is no
miss case to get wrong.** `HabitatRealm` has two variants, so the function is
total by construction rather than by a coverage ratchet, and the
absent-from-the-store default already exists and is already documented —
`HabitatRealm::SURFACE`, the enum's own const, *"the realm a kind absent from
`habitat_realm_registry` carries"*. The species→realm lookup stays exactly where
it is today.

**Consequence for Tasks 4 and 5, so it is not a surprise there:** the resolved
curve is a third species-resolved sleep number, so it belongs in `SleepTraits`
beside `rise` and `afforded_gain`, looked up once at `creature_fatigue` the way
0697 already looks up the other two. That costs **18 full-literal
`SleepTraits { … }` construction sites** (counted: `liveness.rs`,
`tests/suite/fatigue_stock.rs`, `tests/suite/action_module.rs`,
`examples/session_length_scaling.rs`) — all compiler-caught, all mechanical, and
only one of them production. `ConditionResponse` is `Copy + Clone + Debug +
PartialEq`, so every `SleepTraits` derive survives.

**Why a function over an existing registry and not a new 39-row table.** `sleep_grade_registry`'s own doc states the discipline: *"Both halves are read off traits `biosphere_registry` already carries — nothing here invents biology the roster does not already state."* Authoring 39 substrate rows would invent a species axis whose only consumer is this campaign, which is the shape `ObjectProperty`'s "minimal and earned" rule cuts.

```rust
use hornvale_kernel::ConditionResponse;
use hornvale_species::{HabitatRealm, habitat_realm_registry, substrate_response};

/// The Tenon: the substrate response must actually DISCRIMINATE, and in the
/// direction the habitat realm states. A curve that answered the same for
/// both realms would make the whole `(species, thing)` relation rank-1 --
/// separable, and therefore not an edge at all.
#[test]
fn the_two_realms_order_hardness_oppositely() {

    const HARD: f64 = 0.95;
    const FLOOR: f64 = 0.0;

    let surface = substrate_response(HabitatRealm::Surface);
    let under = substrate_response(HabitatRealm::Subterranean);

    assert!(
        surface.eval(SOFT, FLOOR) > surface.eval(HARD, FLOOR),
        "a surface-dwelling kind must prefer the yielding surface"
    );
    assert!(
        under.eval(HARD, FLOOR) > under.eval(SOFT, FLOOR),
        "a subterranean kind must prefer the hard one -- this is the \
         reversal the campaign exists to make expressible"
    );

/// The reversal must survive the LOOKUP, not just the two curves: `drow` and
/// `human` must actually land in different realms. Task 3's curves are
/// useless if every species resolves to the same one, and nothing in the
/// test above would notice.
#[test]
fn drow_and_human_resolve_to_different_realms() {
    let realms = habitat_realm_registry();
    let realm_of = |k: &str| {
        realms
            .get(&hornvale_species::KindId(k))
            .copied()
            .unwrap_or(HabitatRealm::SURFACE)
    };
    assert_eq!(realm_of("drow"), HabitatRealm::Subterranean);
    assert_eq!(realm_of("human"), HabitatRealm::Surface);
    assert_ne!(
        substrate_response(realm_of("drow")),
        substrate_response(realm_of("human")),
        "the campaign's motivating reversal needs these two to differ"
    );
}
```

exercises it. `HabitatRealm` is `Copy + PartialEq + Eq`, so both `assert_eq!`
and `assert_ne!` work on it; `ConditionResponse` is `PartialEq` but not `Eq`,
which `assert_ne!` also accepts.

There is no unknown-species test because there is no unknown-species path:
the function takes an enum.

**Why a BIT comparison is achievable here rather than merely hoped for, and
what it is coupled to.** The controller checked all seven distinct values in
`sleep_grade_registry` (1.50, 1.35, 1.30, 1.20, 1.15, 1.05, 1.00) through
`1.0 + (S - 1.0) * 1.0 * 1.0`: **all seven round-trip bit-identically.** That is
not luck. Multiplying by a literal `1.0` is exact, so the expression reduces to
`1.0 + (S - 1.0)`; and by **Sterbenz's lemma** `S - 1.0` is exact for any
`S` in `[1, 2]`, after which adding `1.0` back recovers `S` exactly because `S`
is representable.

So the identity is a theorem **on the interval `[1, 2]`**, and the table's own
bound is `[1.0, 1.5]` — asserted in `hornvale_species`'s coverage suite, per
`SiteGrade`'s own doc. The two are now coupled: a future grade authored above
`2.0` could break the bit-identity. **Say so in the test's doc comment**, so
whoever raises that bound meets this constraint rather than a mystery red.

- `Substrate::Made` must return a **literal `1.0`** for `fit`, never a curve

  `[0,1]` and can return `0.9999999999999999`; the literal cannot.
- `offer` for `bed` must be the literal `BED_OFFER = 1.0` Task 2 authored, for
  the same reason.
