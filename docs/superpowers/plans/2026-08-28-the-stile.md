# The Stile — one resolver, three corpora, two numbers: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Teach `cli/tests/suite/sentence_corpus.rs` to read both corpus shapes — declared demands and derived demands — and to report coverage per direction, without moving the merchant corpus's score.

**Architecture:** One internal entry type; two readers. A **declared** reader takes `demands` as authored (`the-merchant`, `the-flood-watch`); a **derived** reader computes them as the transitive closure of `presupposes` over `introduces` (`the-ladder`). Coverage reports three buckets — parse, produce, direction-unknown — and direction is never inferred.

**Tech Stack:** Rust 2024, `cli/tests/suite/`, `serde`/`serde_json` only. No new crates.

**Spec:** `docs/superpowers/specs/2026-08-28-the-stile-design.md` — read it first; §3 is the constraint most likely to be violated by accident.

## Task 2: The closure, proven transitive

**Files:** Modify `cli/tests/suite/sentence_corpus.rs`

**Consumes:** Task 1's derived reader.

A rung's demands are the transitive closure of `presupposes`, collecting each reached rung's `introduces`. A **shallow** closure — one level only — is the likely bug and it produces plausible, smaller sets that look fine.

- [ ] **Step 1: Find a rung whose depth discriminates**

You need a rung where the one-level answer and the transitive answer **differ**. The ladder's deepest cumulative sets run to 22 members, so such rungs exist. Find one by reading; report which and both numbers.

- [ ] **Step 2: Write the test against that rung, and run it**

- [ ] **Step 3: Prove the test would catch a shallow closure**

Mutate your own implementation to one level, watch this test fail, restore, and **verify the restore byte-identically** (hash it). A closure test that passes under both depths is worthless.

- [ ] **Step 4: Gate and commit**

## Task 4: Structural assertions for the ladder — and NOT a count

**Files:** Modify `cli/tests/suite/sentence_corpus.rs`

**READ THIS FIRST.** The ladder is `.DRAFT` and **must not be frozen by this campaign**. A frozen entry count *is* the freeze mechanism (`MERCHANT_ENTRIES`), and freezing is the project owner's act — the moment it happens, rung ids become append-only forever.

So: **structural assertions only.** Acyclic; ids unique; no token introduced twice; cumulative closure computable for every rung; exactly two roots. Every one of those holds at any size and freezes nothing.

**Do NOT add a `LADDER_ENTRIES` constant.**

- [ ] **Step 1: Write the assertions**

Acyclicity needs a real graph algorithm, not a backward-reference check — a file can reference only earlier ids and still be acyclic trivially, so a backward-reference test proves less than it appears to. Use a topological sort or DFS colouring.

- [ ] **Step 2: Positively control the cycle detector**

Inject a cycle into an in-memory copy, confirm the detector reports it, and confirm the on-disk file is untouched. A detector that has never fired is not a detector.

- [ ] **Step 3: Gate and commit**
