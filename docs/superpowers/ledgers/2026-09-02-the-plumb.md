#19 [G5] — **RULING: the walk inverts its type filter, because the project's own
discipline is making the tool blind.** Task 3's reviewer found
`Excluded: non-numeric type | 520` covers ~26 authored numbers: `i32`×7, `u8`×7,
`u128`×1 outside `NUMERIC_TYPES`, plus ~11 newtype-wrapped quantities —
`TickSpan`×3, `WorldTime`, `Gyr`, `SurfaceWetness`, `Snowpack`, `Dispersion`.

Two consequences, and the second is why this is a ruling rather than a bug fix:

1. **`REST_BOUT` is invisible.** It is `TickSpan`, so the tool cannot see the
   constant spec §4.4 titles *"the worked example"*. Worse,
   `tools/plumb/src/walk.rs:1-9` says a `pub` filter "would have walked straight
   past both" — true of visibility, false of type, written as though it covered
   both. The campaign's shape, inside the campaign's own tool.
2. **The blind zone GROWS with code quality.** This repo pushes constants toward
   typed newtypes — `type-audit` exists to do exactly that — so every crate that
   improves becomes less visible to `plumb`. An audit whose coverage decays as
   the codebase gets better is worse than no audit, because its silence reads as
   a clean bill.

Decision: **denylist, do not allowlist.** Judge every `const` except those whose
type is declared non-quantity (`&str`, `bool`, `char`, and container/marker
types), rather than admitting a fixed list of numeric primitives. A newtype over
a number is the *most* quantity-like thing in the tree — `Gyr` is a duration —
and the rung question applies to it unchanged. Cost if wrong: the denominator
grows and some entries need a `universal` verdict they would not otherwise have
needed, which is cheap and visible; the alternative is a scanner that quietly
stops seeing the code it was built for.

#25 [G5] — **Ruling: the 33 identifiers/markers leave scope; `Self` ×5 and the

That is not noise. It is a bundle of ratios whose axis of variation is already

#34 [G5] — **Ruling: Task 5 must convert `SLEEP_BOUT` as well as `REST_BOUT`.
Converting one alone INVERTS a semantic ordering the tree asserts, and the test
that guards it cannot see the inversion.** The audit found this; the plan did
not.

The new roster section (fix round 2) lists `SLEEP_BOUT` (`liveness.rs:2462`)
as `per-world` — *"the same wall-clock/local-day-length TickSpan shape as
REST_BOUT"*. Reading that against Task 5's scope makes the consequence exact:

```
REST_BOUT  = TICKS_PER_STD_DAY / 4      = 0.25 std days
SLEEP_BOUT = TICKS_PER_STD_DAY * 2 / 5  = 0.40 std days
```

`liveness.rs:16171` asserts `REST_BOUT < SLEEP_BOUT` — a rest is shorter than a
sleep, which is what the two words mean. Today 0.25 < 0.40 holds.

Task 5 makes `REST_BOUT` a quarter of the **local** day while `SLEEP_BOUT`
stays a fixed fraction of the **standard** day. The ordering then requires
`L/4 < 0.4`, i.e. **`L < 1.6` std days = 38.4 hours**. `RotationPin::PeriodHours`
admits **4-100 hours**, so across most of the legal range a rest becomes
*longer than a sleep*.

**And nothing goes red.** The assertion reads the two constants, so it
evaluates at the standard-day case forever; the inversion is a property of the
runtime span on a slow world, which no test constructs. Task 5 as planned would
ship a world where resting takes longer than sleeping, under a green suite,
having just fixed a different calibration in the same function.

So the conversion is not optional for the pair: **both convert, or neither.**
Converting only `REST_BOUT` is strictly worse than converting neither — today
the two are consistently wrong together and their ordering holds; afterwards
they are inconsistently wrong and it does not.

Task 5 additionally owes an ordering test that evaluates the two spans at a
**runtime** `L`, not at their compile-time values. The existing assertion is
not wrong, it is just blind past `L = 1`, and it is the shape of test that let
this sit unnoticed.

This modifies the brief's "REST_BOUT is the sole exception" clause. The clause's
REASON — convert only what is a named regression with a measured bound — is
unchanged and is what forces the expansion: the bound is the ordering, and it is
measured above.

Standing lesson: **converting one half of a paired constant is a different act
from converting a lone one.** A pair encodes a relation, and a relation
asserted over compile-time values is invisible to exactly the change that
breaks it.
