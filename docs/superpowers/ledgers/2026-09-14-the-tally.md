# The Tally — decision ledger

A chamber log's failure list is read through a pipe, and every pipe can
truncate. A truncated list reads exactly like a complete one.

Provenance, all on 2026-09-14 and all by the same operator:

- `sluice-mouth.sh … | tail -3` produced a confusing overlap advisory —
  reproducing the defect `scripts/sluice-vet.sh`'s own header was written to
  prevent, quoted in that header as having cost campaign/the-legend a retracted
  claim post.
- A token-diff of two census blobs printed eight differences and elided the
  rest; the ninth was `source_revision`, and stopping at eight would have
  inverted the diagnosis from *the world moved* to *a stale build*.
- `grep … | tail -8` reported **7 failures** for two runs of
  campaign/the-tidemark that had **20** and **17**. The campaign was told it
  had four stragglers when it had seventeen, and told nothing about the three
  its own change had fixed.

---

#1 [G1] — **What stops a truncated failure list being quoted as the whole?**
· **Decision:** a reader that cross-checks its own extraction against the run's
own `Summary` line and REFUSES when the list is shorter, rather than printing a
plausible subset. · **Why:** every prior remedy in this family has been an
instruction to a person — "never truncate the mouth", stated three times in a
file I had not read — and attention keeps losing to attention. Two independent
readings of one log (the greppped list, the count nextest printed) can disagree,
and the disagreement is mechanically detectable. That catches a truncated pipe,
a mis-written regex, and a log-format change, without the reader having to
suspect any of them. · **Alternatives discarded:** documenting the hazard again
(the documentation exists and I violated it while quoting it); making the
existing greps longer (moves the cliff, does not remove it); asserting an exact
equality between list and count (wrong — nextest prints each failure twice and
a log holds several invocations, so over-count is normal and only UNDER-count is
the defect). · **ideonomy passes / overturns:** 1 / 1 — the overturn was exact
equality to a one-sided floor, which is the difference between a check that
works and one that cries wolf on every real log.
· **Capture:** this entry; `scripts/sluice-failures.sh`.

#2 [G1] — **Should it also diff membership between two runs?**
· **Decision:** yes, as an optional second argument. · **Why:** the same night
produced the companion error. Two runs failed 20 then 17, and "three fixed" is
the natural reading of those two numbers — true here, and not what the numbers
show. A run can fix three, break three, and hold at 20. Only the set difference
distinguishes them, and this repo has the failure written down already (a
roster held its SIZE while members swapped, three times in three unrelated
subsystems). · **The previous log is cross-checked too**, because a truncated
BEFORE-log fabricates FIXED entries — the most confident possible wrong answer.
· **ideonomy passes / overturns:** covered by #1's pass.
· **Capture:** this entry.

## Follow-ups

- Nothing calls `sluice-failures.sh` automatically. That is deliberate for now —
  it is an operator's reading tool, not a gate — but it is the same shape as
  `sluice-vet.sh` sitting unrun, and The Usher's answer there was to surface it
  at the moment of need. The candidate moment here is a CHAMBER RED: the drain
  loop already writes the log path into the held row's note, and could run this
  instead of naming a file.
- The extraction assumes nextest's `FAIL [` prefix and that a test path is the
  line's last field. A libtest-only run (`cargo test --doc`) does not match, and
  this will report zero failures for one. It does not pretend otherwise — the
  cross-check catches it, because a doctest failure prints no `Summary [` line
  either, so the "cannot run" arm fires rather than a false all-clear.
