# The Usher — decision ledger

`scripts/sluice-vet.sh` does the whole pre-dispatch vet — the mouth in full,
decisions and their block, cross-branch decision collisions, the surfaces that
cost a chamber run when missed, Definition of Done, the close package, and
whether the operator's own checkout is fast-forwarded. Nothing runs it.

Provenance: an operator (me) ran this queue for a full session — six vets,
seven merges — without knowing the script existed, hand-rolling a worse vet
each time. Including, on 2026-09-13, piping the mouth through `tail -3` and
getting a confusing overlap advisory: the exact defect this script's own header
says it was written to prevent, reproduced by someone who had not read it.

---

#1 [Q] — **Should the vet gate dispatch instead of reporting?**
· **Decision:** no. · **Why:** the script states the opposite in three places,
with a reason — *"this script REPORTS, it does not gate … duplicating that
decision here would give two places to disagree about whether a candidate may
run"* — and `sluice-drain.sh` already consumes the mouth's verdict. Adding a
second authority is the defect the comment names. · **Alternatives discarded:**
a machine-readable verdict line the drainer gates on (same two-authorities
problem, and most of what the vet reports is judgement-shaped: a `disposition`
still reading `active`, a census branch carrying a campaign).
· **ideonomy passes / overturns:** 1 / 0. · **Capture:** this entry.

#2 [G1] — **Then what closes the gap?**
· **Decision:** automate the vet's PRODUCTION at submission; leave its
consumption human. A repo-level watcher notices a newly queued row and prints
`sluice-vet.sh` for it. · **Why:** the graph has one missing edge and it is
`submission → vet`, not `vet → dispatch`. · **ideonomy passes / overturns:**
1 / 1 — and the overturn is of my own earlier proposal, which makes it worth
stating plainly.

  **I proposed a "wait-and-take-one" drainer** so the operator would stop
  hand-chaining bounded drainers (three times in one session). The
  reversibility axis killed it: a wrongly dispatched merge costs a SLOT, not
  correctness — the chamber never pushes on red and its kill path is tested
  (rc=143, claim released, main unmoved). So the friction of hand-dispatch is
  not protecting against damage. **It is the only mechanism that makes the vet
  get read.** Automating dispatch would have deleted the gate while leaving the
  script exactly as unrun as it was all session — a strictly worse outcome
  reached by fixing the friction I happened to notice rather than the gap that
  was actually costing something.

· **Alternatives discarded:** submissions arriving `held` and an operator
flipping them to `queued` (inverts submission semantics for stage and census
too, which auto-drain correctly today); an allowlist of vetted request ids (new
state, and it encodes the decision in a file rather than in a person).
· **Capture:** this entry.

#3 [Q] — **Where does the watcher live?**
· **Decision:** the repository, not an operator's scratchpad.
· **Why:** this is The Watchman's finding, one layer on. That campaign moved the
drain LOOP into the repo because a scratchpad loop doing real gating work was
invisible and outlived its session; the session that landed it then wrote its
new-submission watcher into a scratchpad. Same shape, same week.
· **ideonomy passes / overturns:** covered by #2's pass.
· **Capture:** this entry.

## Follow-ups

- The watcher reports and does not dispatch, so a submission can still sit
  while nobody is at the terminal. That is the accepted cost of #2: the queue
  is operated, not autonomous.
- `sluice-vet.sh` reports `operator checkout: … (== origin/main: NO — ff before
  draining)`. Nothing enforces it. Worth knowing that the vet can tell you your
  own checkout is stale and you can still dispatch.
