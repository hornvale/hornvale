# 0187. A pre-genesis sky query is clamped to genesis, deliberately

**Status:** Accepted (2026-08-23) · **Decider:** Nathan · **Campaign:** The
Escapement · **Supersedes:** nothing

In the context of `hornvale-astronomy`'s one crossing from `WorldTime` to
`StdDays` (`GeneratedSky::t`, `provider.rs`) inheriting a bare
`time.day().max(0.0)`, justified only by a code comment
("genesis-time queries never predate the world"), and facing The Escapement's
retype of `WorldTime` to an exact tick count — which forces every such comment
to become either a recorded choice or a bug — we decided that **a pre-genesis
sky query answers as genesis, by clamping the negative time to zero rather
than returning an `Option` or an error**, accepting that a caller cannot
distinguish "the sky at genesis" from "the sky before genesis" through this
API.

**What was inherited.** The clamp predates this campaign and was never a
decision on record — only a comment beside the code. Nothing would have
noticed if the clamp were removed, inverted, or replaced with a panic; no
test exercised the negative branch at all.

**What was traced.** No caller can reach the negative path today.
`GeneratedSky::t` is the domain's only `WorldTime -> StdDays` funnel, and it
clamps. The only sites in the workspace that bypass the funnel and construct
a `StdDays` directly for a sky/calendar query (`windows/worldgen/src/lib.rs`,
two call sites) pass a hardcoded `StdDays::new(0.0).unwrap()` — genesis
itself, never a negative value. So the clamp is exercised only by a
deliberately pre-genesis instant, which no production caller constructs.

**The third alternative doesn't exist at the public boundary, and that is
the stronger reason to clamp.** `StdDays::new` is generated by the
`non_negative` arm of `units.rs`'s `quantity!` macro and rejects any negative
value outright, so **no caller outside `domains/astronomy` can construct a
negative `StdDays` at all** — "pass the negative time through unclamped" is
not a live option at that boundary, full stop. Precision matters here: the
clamp is not literally *forced* at `GeneratedSky::t`'s own call site, because
that site builds its `StdDays` through the `pub(crate)` tuple field
(`StdDays(time.as_std_days().max(0.0))`) and so bypasses `new` — nothing at
the Rust level stops `GeneratedSky::t` itself from constructing a negative
`StdDays` internally, the way `eclipses.rs`'s node/phase arithmetic already
does. The constraint binds at the *public* boundary the funnel sits in front
of, not at the funnel's own implementation. A future reader who mistakes
those for the same claim might reasonably conclude the clamp is free to
delete; it is not — deleting it would still leave every *internal*
construction path free to hand a negative `StdDays` downstream, which is
exactly the landmine Task 5 found and fixed in `Calendar::local_day`.

**The tension with Task 5, engaged rather than papered over.** An earlier
draft of this record justified the clamp by calling a pre-genesis sky "not a
physical question." That claim does not survive contact with this
campaign's own sibling task: `Calendar::local_day` (Task 5, same commit) was
deliberately fixed to answer correctly for negative time, on the strength of
decision 0126's own precedent — a day is a point on an axis, not a duration,
and a founder can be born (and, by the same logic, a calendar can report a
local day) before the history record begins. If the calendar is allowed a
well-defined pre-genesis answer, "not a physical question" cannot be the
reason the *sky* draws a different line; the sky and the calendar sit on the
same time axis. The reason that actually holds is the structural one above:
the public API cannot receive a negative `StdDays` to answer honestly in the
first place, so the choice is between clamping (a total function with no
case to defend) and defending a case the type system already forecloses.
That is not a claim about physical meaning — it is a claim about where the
constraint already lives.

**The choice, and why not the alternatives.**

- **Clamp to genesis (chosen).** Given that `StdDays::new` already forecloses
  a negative value at the public boundary, clamping the internal, pre-`new`
  computation to the same non-negative range `StdDays` will accept anyway
  costs nothing and gives every caller a total function with no failure mode
  to handle, for a case no caller can actually produce.
- **Return `Option<SkyReport>` or an error.** Rejected: it would force every
  one of `sky_at`'s callers (several, across `windows/`) to handle a case
  that is unreachable today, in exchange for defending a query the public
  `StdDays` boundary already refuses to accept either way. An error return
  does not make the negative instant more receivable than genesis does — it
  just relocates the clamp's judgment call from this function to every
  caller.

**Consequence.**

- `GeneratedSky::t` (`domains/astronomy/src/provider.rs`) is ported to the
  tick-shaped surface (`WorldTime::as_std_days`) as a pure rename — the clamp
  itself is unchanged, now stated as a decision rather than a comment.
- `domains/astronomy/src/provider.rs`'s own test module holds
  `a_pre_genesis_query_has_a_documented_answer`, the first test to assert the
  clamp's behavior rather than merely state it in prose.
- The NaN half of the old `max(0.0)` guard (`f64::max`'s NaN-to-0.0
  semantics) is gone by construction: `WorldTime` is built from an integer
  tick count and cannot hold NaN.
