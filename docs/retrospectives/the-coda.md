# The Coda — retrospective

Process, not product. The product is the
[reconciliation table](../../docs/audits/campaign-reconciliation.tsv) and its
[chronicle](../../book/src/chronicle/the-coda.md).

## Presence is not closure

The repository already had useful local documentation checks, including an
exact spec-plan matcher. It was tempting to read a matching path, a checkbox,
or the mere presence of a chronicle as proof that a campaign was closed. None
of those is a closure argument. The existing matcher deliberately excluded a
named population; expanding its apparent success by guessing aliases would
have replaced a known blind spot with false positives.

The durable correction is a separate, executable population: every direct
Markdown child in the four primary record directories has exactly one table
entry, and every entry carries its own evidence. A direct source declaration
of a terminal chronicle, or an exact shared campaign identifier, can establish
a relationship. Loose filename similarity cannot. The Task 3 review mattered:
it rejected a heading-only conversion pass and made the rule direct before it
became a historical claim.

## Retain evidence; route only real residue

The audit found no `unresolved` product direction, so it added and deduplicated
zero registry rows. That is a result, not missing work. An active record still
has its own concrete home; a process lesson belongs here; and an ordinary
repair belongs with the campaign that owns it. Promoting all three to the idea
registry would make that registry less truthful while leaving the original
evidence harder to read.

The practical lesson is to distinguish three questions every time a campaign
looks complete: is the record present, is there direct evidence of closure,
and is there a durable future-facing residue? Only the last question can add a
registry row. Only the second can close the audit row. Neither authorizes
deleting the first.
